# API: backend foundation

Base URL: `http://127.0.0.1:3100`. All routes except `GET /health` require `Authorization: Bearer <configured token>`. Tokens are generated by `npm run setup`; tokens are never accepted as body fields. A principal has an explicit trade-ID allowlist. Buyer and broker use different tokens.

Imports and proposals require an `Idempotency-Key` header of 8–128 ASCII letters, numbers, hyphens or underscores. Repeating an identical request returns its original response, even after restart. Reusing the key with another URL or payload returns `409 IDEMPOTENCY_CONFLICT`. Keys are scoped to tenant + principal. Comparison is read-only and does not need an idempotency key.

| Method | Path | Behavior |
|---|---|---|
| GET | `/health` | Process health and explicit integration status |
| POST | `/imports` | Atomic, role-scoped CSV import |
| GET | `/trades/:id` | Original rows, revision and proposal history |
| POST | `/trades/:id/compare` | Deterministic two-book comparison; no write |
| GET | `/trades/:id/reconciliation` | Comparison, latest candidate and missing integration evidence |
| POST | `/trades/:id/proposals` | Create a candidate; never apply it |
| GET | `/trades/:id/audit` | Ordered successful mutation history |
| POST | `/trades/:id/verification-challenges` | Human approvers only, once World ID is configured: a signed request for the latest candidate |
| POST | `/trades/:id/world-id-verifications` | Verifies the complete IDKit result with World; succeeds only with a trust adapter |
| POST | `/trades/:id/approvals` | Explicit approve or reject after verification; the second approval stages the correction |
| POST | `/trades/:id/agreement-commitments` | Closed pending bilateral approval and Move enforcement |
| POST | `/trades/:id/funding-intents` | Closed pending confirmed agreement |
| POST | `/trades/:id/settlement-instructions` | Closed pending confirmed agreement and funded escrow |

Agents always receive `403 AGENT_AUTHORITY_DENIED` on these paths. Without World ID configuration, development human principals receive `503 INTEGRATION_NOT_READY`. With World ID but no trust adapter, a verified proof receives `503 PRESENCE_AND_ENROLLMENT_UNCONFIRMED`. The only shipped adapter is the demo roster, which is opt-in (`TRADEBRIDGE_DEMO_APPROVERS`), staging-only and labelled in `/health`, `/integrations` and the UI ([INTEGRATIONS.md](INTEGRATIONS.md#world-id)). There is no mock bypass or force-approve option. The final commitment route will be service-only; the current closed route grants nobody commitment authority.

## Import example

After `npm run setup` and starting the server, run this in a separate terminal at the repository root. It reads credentials without printing them:

```sh
node --env-file=.env --input-type=module <<'JS'
import { readFileSync } from 'node:fs';
const principals = JSON.parse(process.env.TRADEBRIDGE_PRINCIPALS);
for (const [side, revision] of [['buyer', 0], ['broker', 1]]) {
  const principal = principals.find(p => p.id === `${side}-agent`);
  const response = await fetch('http://127.0.0.1:3100/imports', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      Authorization: `Bearer ${principal.token}`,
      'Idempotency-Key': `first-import-${side}`,
    },
    body: JSON.stringify({
      csv: readFileSync(`data/${side}.csv`, 'utf8'),
      expected_revisions: { 'TB-001': revision },
    }),
  });
  console.log(response.status, await response.json());
  if (!response.ok) break;
}
JS
```

Initial revision is 0. Buyer import advances it to 1, broker import to 2, and the first proposal to 3. **Storage revision is distinct from trade version:** original source terms are v1; the first proposed correction is v2. Read the current trade revision before a new write. Retrying a request uses the original key and payload.

CSV files contain 1–100 records. Header order is flexible, but the following headers must appear exactly once; extra headers are rejected:

```text
trade_id,instrument_id,fill_id,buyer_address,broker_address,buyer_recipient,broker_recipient,bond_type,cash_type,quantity,unit_price_base,accrued_interest_base,fees_base,net_cash_base,settlement_date,expires_at,account_ref,external_reference
```

Amounts are canonical nonnegative decimal integer strings, bounded to u64. Quantity, unit price and net cash must be positive. Quantity has zero decimals; cash has two. `unit_price_base` is cash base units per bond base unit. So `1000` price means 10.00 DEMOUSD and `1000000` net means 10,000.00 DEMOUSD. Only the configured synthetic demo asset types are accepted. No asset IDs are inferred from symbols.

Net cash must equal `quantity × unit_price_base + accrued_interest_base + fees_base`, with no overflow. Addresses are full lowercase `0x` + 64 hex characters and cannot be zero. Dates use `YYYY-MM-DD`; expiry uses UTC `YYYY-MM-DDTHH:mm:ssZ` and must be future-dated. Different fills need distinct trade IDs in this first milestone.

Original CSV files are stored privately; a trade read returns only its own raw record and file-hash reference, so a multi-trade CSV cannot expose unrelated rows. Both principals scoped to a bilateral trade can inspect its two records; selective field disclosure is future work.

## Proposal body

```json
{
  "expected_revision": 2,
  "terms": "a full economics object, not a patch",
  "reason": "Align the broker confirmation with the original buyer order."
}
```

`terms` above is descriptive: supply the complete JSON object matching the CSV fields except `account_ref` and `external_reference`. These references are carried from the preserved buyer/broker evidence. The source's `trade_id` must equal the URL ID. The server adds version, tenant, chain/package/registry context, decimal conventions, source IDs and both account/external references before hashing. Client-supplied approval, hash, network, or version overrides are rejected.

Response: `{ candidate, revision, status: "HUMAN_VERIFICATION_REQUIRED", canonical_changed: false }`. Changing any bound terms creates another version and hash. No approval material exists yet, and no candidate can be funded.

Common errors: `400 VALIDATION_FAILED`, `400 INVALID_CSV`, `400 TRADE_EXPIRED`, `400 UNSUPPORTED_ASSET`, `401 UNAUTHENTICATED`, `404 NOT_FOUND`, `409 STALE_REVISION`, `409 SOURCE_EXISTS`, `409 IDEMPOTENCY_CONFLICT`, `413 INVALID_REQUEST`.

## Browser and World ID routes

All API paths are also available under `/api/` for the same-origin browser client. `POST /session` accepts a development token and sets an opaque one-hour HttpOnly, SameSite Strict cookie. `GET /session` exposes only public session metadata. `POST /session/demo` creates isolated synthetic records when local demo mode is enabled; `DELETE /session` signs out and removes demo working data (its append-only audit is retained). Browser write origins are checked. The app remains loopback-only. `GET /trades` lists the principal's permitted records and `GET /integrations` reports actual configuration readiness.

When World ID is configured, a human principal may request `POST /trades/:id/verification-challenges` with `expected_revision`, `terms_hash`, and an idempotency header. The response contains a signed RP context, the World ID action and the signal for the current candidate. Each candidate version has its own action, `<WORLD_ACTION>-<32 hex>`, because World ID 4.0 uniqueness proofs are one-time per person per action. `POST /trades/:id/world-id-verifications` accepts `{ challenge_id, proof }`, forwarding the complete IDKit result only after local context validation. A challenge can be submitted once; failures require a new challenge. If the proof's nullifier already verified for the other side of the same version, the response is `403 SAME_PERSON_BOTH_SIDES`. A valid World proof still receives `503 PRESENCE_AND_ENROLLMENT_UNCONFIRMED` while no trust adapter is injected. Commitment, funding and settlement routes stay closed.

### Model runs and internal services

`POST /trades/:id/agent-runs` requires an agent principal, `Idempotency-Key`, and `{ "expected_revision": 2 }`. A configured model may read its own source, request deterministic comparison and create one candidate. Same-key retries return the recorded result or an unresolved-run error, never rerun tools. A provider key alone does not trigger requests; the user must invoke the run.

`POST /trades/:id/approvals` accepts `{ expected_revision, challenge_id, version, terms_hash, decision: "approve" | "reject" }` only with a server-injected staff authority and an already verified, unused challenge. Default runtime returns 503. Agents always receive 403. The response adds `correction`: `null` until both sides approve the same version, then `{ staged: true, instruction_id, version, state }`, or `{ staged: false, error, message }` if staging was refused after the decision was recorded.

`ConsentService.stage` and `CommitWorker` are internal service APIs, with no agent/human HTTP execution capability. The approvals route calls `stage` itself after the second approval; no caller chooses what is staged. Staging consumes both approvals and writes canonical terms and one instruction atomically. The reconciliation response returns only public commitment status/digest/object, never signed bytes or identity bindings.
