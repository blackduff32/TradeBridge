# Two-Agent Trade Reconciliation and Settlement — Revised PRD

**Version:** 0.2 · 25 September 2026  
**Audience:** hackathon developers and judges  
**Status:** proposed implementation; supersedes the workflow in `trade_reconciliation_settlement_prd.md`  
**Primary prize target:** Curvegrid — Best AI Agent Project (based on the event brief supplied by the team)  
**Working name:** TradeBridge

## 1. Product in one sentence

Two independently operated trade agents—one representing the buyer's desk and one representing the broker—compare their own trade records, exchange evidence-backed proposals, stop mismatched settlements, and submit only a jointly approved version for tokenized-asset settlement and post-trade reconciliation.

**Important distinction:** These are *buyer-side* and *broker-side* agents, not two agents owned by the broker. They act for different principals, have different source records and credentials, and must not be able to approve each other's position. If the team literally means two brokers, replace the principal roles and economics before implementation.

Atomic settlement ensures all-or-nothing execution under encoded rules; it does not guarantee agreement on price, correct booking, or eventual settlement. This product binds an agreed trade version to settlement and separately checks what actually moved and what each party recorded.

## 2. Judge-visible happy and blocked paths

### The mismatch demo

1. **Buyer-side agent** loads an authenticated internal order: buy **1,000 tokenized bond units** at an illustrative agreed unit price of **10 cash-token units**, so illustrative gross cash is **10,000**, before fees/accrual. This is clearly labeled synthetic demo data.
2. **Broker-side agent** loads its own confirmation: **1,100 units** at the same illustrative price. Both agents preserve their raw records, issuer/provenance, timestamps and source-row IDs.
3. Agents exchange only the necessary normalized terms and evidence references through a shared negotiation thread. Both independently compare instrument, token IDs, sides, quantity, price convention, fees/accrual, settlement date and destination.
4. The buyer agent flags `QUANTITY_MISMATCH: 100 units`; the broker agent acknowledges the differing records. The policy engine returns `BLOCKED_MISMATCH`, and the settlement endpoint refuses a submit attempt. No signer call or contract transaction occurs.
5. The broker agent proposes a correction to **1,000 units** with an explanation and source evidence. The buyer agent verifies the proposed terms against its source; the proposal is not itself consent.
6. Because changing 1,100 to 1,000 units is material, the broker's authorized human approver confirms the amended broker version. The buyer's authorized human approver approves the matching canonical version. For the demo, require approval by **both** parties for this material correction even if one agent's initial record already matched.
7. Both approvals bind to the same canonical version and `terms_hash`; the policy engine verifies both actors, role, hash, version, expiry and escrow/hold state. Only then does the operator submit an idempotent settlement instruction.
8. On the configured Hedera environment, the contract performs the available same-chain bond-versus-cash transfer. The verifier checks receipt status and the underlying bond/cash token movements, then the reconcilers mark each book `SETTLED` or raise a missing-book-update exception.

**Demo truthfulness:** If the deployed contract cannot verify approval hashes or reciprocal economic terms on-chain, explicitly say the application policy enforces them *before submission* and the contract enforces only its encoded DvP rules. Do not describe an off-chain guard as an on-chain invariant.

### A second denied path

Submit a changed 1,100-unit version after the 1,000-unit agreement. Its hash does not match the approved version: return `BLOCKED_UNAPPROVED_VERSION` before signing. The blocked path should be generated by a real policy check, not by hiding a UI button.

## 3. Roles, trust and permissions

| Role | Reads | Can propose | Can authorize |
|---|---|---|---|
| Buyer-side agent | Buyer's source record; shared evidence thread; permitted settlement data | Mismatch report, canonical terms, buyer book-update proposal | No final trade approval or contract signature |
| Broker-side agent | Broker confirmation; shared evidence thread; permitted settlement data | Amendment, explanation, broker book-update proposal | No final trade approval or contract signature |
| Buyer human approver | Buyer record, agreed diff, evidence and policy | Correction request | Approves exact buyer-side canonical version/hash |
| Broker human approver | Broker record, agreed diff, evidence and policy | Correction request | Approves exact broker-side canonical version/hash |
| Settlement operator/service | Approved instruction and validated holds | Idempotent submission | Uses a scoped signer only after backend preflight; cannot invent approved terms |
| Reviewer/operations | Exceptions and permissioned audit history | Book adjustment or recovery action | Approves corrections according to role policy |

Agent-generated text is not evidence. Agent tools must be scoped to the actor and tenant. Neither agent can forge the other's source row, approval or signature. The shared negotiation log records which party sent each proposal and when.

## 4. Canonical agreement and negotiation

**Required fields:** shared trade ID; internal ID and broker reference; instrument identifier and bond token; buyer, broker/seller and destination wallets; allocation account reference; quantity; unit price and price convention; gross cash; accrued interest; fees; net cash; cash token/currency; settlement date; version; fill IDs; approval actor and time; hold/escrow reference; settlement instruction ID.

**Canonical serialization:** use a versioned schema and fixed integer token base units. Compute `terms_hash = H(schema_version || canonical_terms)`. Avoid floating-point calculations and exclude untrusted free text from executable economics. An amendment creates `v2` and invalidates approval of `v1` for that instruction; approvals must be attributable, authenticated and bound to the exact trade ID, network, terms and expiry. A hash proves the approved data stayed unchanged, not that the original records were right.

**Negotiation states:** `IMPORTED → COMPARED → MISMATCH / MATCHED → AMENDMENT_PROPOSED → PENDING_BUYER_APPROVAL / PENDING_BROKER_APPROVAL → AGREED → RESERVED → SUBMITTED → CONFIRMED / REVERTED / UNKNOWN → RECONCILED`. A disagreement cannot enter `AGREED` merely because the two agents produce the same text; approvals come from authorized principals. A failed or uncertain transaction does not imply that the agreement has expired unless policy explicitly says so.

**Material amendment policy for MVP:** any change in quantity, unit price, net cash, instrument/token, buyer/seller, allocation, date or destination requires new approval by both parties. Numeric tolerances can classify rounding differences for analyst review but cannot silently change settlement instructions. Missing or contradictory source information blocks the flow.

## 5. Agent design and messages

**Agent inputs:** each side receives its own normalized trade record and limited shared counterparty evidence, not unrestricted access to the other's private book. A deterministic comparator calculates field-by-field differences; the language model may explain or propose a resolution, but cannot override the comparator or authorize settlement.

**Allowed tools:** `get_local_trade`, `get_shared_version`, `compare_terms`, `get_evidence`, `send_proposal`, `get_counterparty_response`, `request_human_approval`, `get_hold_status`, `get_settlement_status`, `propose_book_update`. Tool outputs include provenance, timestamp and version.

**Protected tools:** `approve_terms`, `reserve_order`, `submit_settlement`, `cancel_order`, `write_book` require server-side role checks and explicit authorization. The agent must not access signing secrets. A tool call rejected by policy produces an audit event and visible reason.

**Message envelope:** `{message_id, sender_role, trade_id, version, proposal_type, field_diffs, evidence_ids, timestamp, previous_message_id}`. Deduplicate messages by ID, sign or authenticate the origin, and prevent a reply to an obsolete version from silently changing the current one. Treat imported CSV cells and counterparty messages as untrusted data, never as instructions to the agent or operator.

**Explainability bar:** each agent proposal names the field, each party's value, the raw source-row reference and the proposed correction. Example: “Quantity differs: buyer order 1,000 units (row B-01), broker confirmation 1,100 units (row S-01). Hold settlement; request broker correction and both-party approval of v2.”

## 6. Settlement and post-settlement controls

**Preflight before any signing:** both human approvals match the same terms hash/version; reciprocal buyer/seller roles; approved token IDs, quantities, gross/net cash and limits; correct order and hold ownership, asset, amount, expiry and escrow; compliance result; no existing consumed instruction; atomic reservation of fill IDs. The supplied review of `MatchingEngine.settle()` at commit `a45e83f` indicates trade-ID equality alone does not prove reciprocal economic agreement. Recheck the final code; do not rely on trade ID alone.

**Idempotency:** persist a stable `settlement_instruction_id` before sending. A retry returns the existing attempt or reconciles its observed state; a timeout is `UNKNOWN`, never automatic `FAILED`. Verify receipt execution status, exact settlement event position, and independent bond/cash movements before marking `CONFIRMED`. Preserve failed/uncertain orders for investigation rather than deleting them optimistically.

**Book reconciliation:** compare (A) buyer record, (B) broker confirmation, (C) approved version and (D) observed movement. Emit separate `SETTLED_BOOK_MISSING`, `CASH_MISMATCH`, `QUANTITY_MISMATCH`, `FAILED_SETTLEMENT` and `UNKNOWN_OUTCOME` exceptions. Propose idempotent updates for both books; no invisible automatic correction. The separate Arc referenced cash path is not claimed as atomic Hedera–Arc DvP.

## 7. APIs and data model

**Core records:** `SourceRecord`, `NormalizedTrade`, `NegotiationMessage`, `TradeVersion`, `Approval`, `MatchGroup`, `Hold`, `SettlementInstruction`, `SettlementAttempt`, `TransferEvidence`, `BookUpdateProposal`, `ExceptionCase`, `AuditEvent`.

| Endpoint (proposed) | Purpose |
|---|---|
| `POST /v1/trades/import` | Import buyer/broker CSV with party authorization, raw-row preservation and validation |
| `POST /v1/trades/{id}/compare` | Return deterministic differences and coverage |
| `POST /v1/trades/{id}/messages` | Submit authenticated, version-bound agent proposal/evidence |
| `POST /v1/trades/{id}/versions` | Propose immutable canonical terms/version |
| `POST /v1/trades/{id}/approvals` | Human-authenticated approval of an exact version/hash |
| `POST /v1/trades/{id}/settlement-instructions` | Policy-checked idempotent reservation/submission; reject mismatches |
| `GET /v1/trades/{id}/settlement` | Receipt, transfer evidence, uncertainty and retry status |
| `GET /v1/trades/{id}/reconciliation` | Four-way diff, cases and proposed book updates |
| `GET /v1/trades/{id}/audit` | Source and approval versions, messages, settlement and corrections |

All mutations use authorization, idempotency keys and version checks. Private books must not be publicly exposed through a shared API. Store exact money amounts as base-unit integer strings, preserving the original display convention.

## 8. Acceptance tests

| ID | Test | Required result |
|---|---|---|
| AT01 | Buyer 1,000 vs broker 1,100 units | 100-unit mismatch shown with two source references; settlement denied before signer |
| AT02 | Agents agree verbally without human approvals | Still blocked |
| AT03 | Broker approves v2 but buyer approves v1 | Hash/version mismatch; still blocked |
| AT04 | Both authorized humans approve identical v2 | May proceed only if all hold, economics and compliance preconditions also pass |
| AT05 | Post-approval quantity, price, address or cash changes | Approval invalidated; signer not invoked |
| AT06 | A forged counterparty message or cross-tenant data request | Authentication/authorization rejects it |
| AT07 | Duplicate agent proposal or settlement request | No duplicate approval, reservation or transfer |
| AT08 | RPC timeout after transaction succeeded | Existing instruction recovered; no new trade ID or double settlement |
| AT09 | Receipt reverts or transfer amounts differ | Not marked confirmed/reconciled; exception raised |
| AT10 | Chain settled but buyer or broker book remains pending | Separate missing-book exception and proposed replay/update |
| AT11 | AI explanation cites a fabricated fee | Proposal rejected or marked unsupported; deterministic diff unaffected |
| AT12 | Same-block identity/compliance update | Verifier checks ordering at exact settlement event position |

**Minimum working demo:** AT01–AT05 plus one actual successful settlement evidence check and one post-settlement four-way comparison. If time is constrained, cut extra charts and additional assets before cutting the real denial and approval logic.
